# NurumayuEditor Plan B
## 「Typoraに近い完成度」にまだ届いていない理由と、到達するための実装計画

作成日: 2026-08-01

---

## 1. 結論

現在のNurumayuEditorは、次の意味では実用的なMarkdown Editor / Previewです。

- `.md` / `.markdown`を直接開いて保存できる
- CodeMirrorでMarkdown原文を編集できる
- Edit / Split / Previewを切り替えられる
- GFMの表、タスクリスト、コード、リンク、画像をプレビューできる
- Mermaidをプレビューできる
- Markdown原文を既存の段落、AI、スライド機能へ投影できる

しかし、Typoraの中心的な価値は「ソースエディタとプレビューを並べること」ではありません。

Typoraに近い状態とは、Markdown原文を正本として保持しながら、同じ編集面の中でMarkdown記号を必要なときだけ見せ、文章を直接編集しているように感じられる状態です。

現在のNurumayuEditorは、

```text
左: Markdownソース
右: HTMLプレビュー
```

という一般的な二画面型エディタです。

Typora型は、

```text
1つの編集面
  ├─ カーソルがない場所: 装飾済みの文章として表示
  └─ カーソルがある場所: Markdown記号を表示して編集
```

です。

この操作モデルの違いが、現在の実装を「Markdown Editor / Preview v1」とは呼べても、「Typoraに近い完成度」とはまだ呼べない最大の理由です。

---

## 2. 現在できていること

### 2.1 Markdown原文の編集

`src/components/MarkdownEditor.tsx`でCodeMirror 6を使用しています。

対応済み:

- Markdown構文ハイライト
- 行番号
- 折り返し
- CodeMirror内のUndo / Redo
- Edit / Split / Preview切り替え
- 日本語入力

### 2.2 Markdownプレビュー

`react-markdown`と`remark-gfm`を使い、次を表示できます。

- 見出し
- 段落
- 太字、斜体
- 箇条書き、番号付きリスト
- 引用
- リンク
- インラインコード、コードブロック
- GFMテーブル
- GFMタスクリスト
- 画像
- Mermaidコードブロック

### 2.3 Markdownファイルのライフサイクル

対応済み:

- `.md` / `.markdown`の直接オープン
- 開いたMarkdownファイルへの上書き保存
- Rust側でのアトミック書き込み
- `.aix`内へのMarkdown原文保存
- Markdown原文から段落・見出し・画像・Mermaidチャンクへの投影

### 2.4 既存機能との接続

Markdownを編集しても、既存の次の機能を利用できます。

- 段落単位AI処理
- スライド表示
- Mermaid表示
- Markdown / PDF / PPTXなどの書き出し
- Undo / Redo
- 複数タブ
- セッション復旧

これらは強い土台です。以下は、この土台の上にTypora型の編集体験と常用時の安全性を追加する計画です。

## 3. Typoraに近い完成度に届いていない具体的な理由

## 理由A: WYSIWYM編集ではなく、ソースとプレビューが分離している

現在はMarkdownソースを編集し、別領域で結果を確認します。

未実装:

- 非アクティブな見出しの `#` を隠す
- 非アクティブな太字の `**` を隠す
- 非アクティブな斜体、打ち消し線、リンク記号を隠す
- リスト記号や引用記号を視覚的に整える
- カーソルが入ったブロックだけMarkdown記号を再表示する
- 編集位置と装飾位置をずらさずに維持する

Typoraらしさの中心はこの部分です。プレビューの見た目を改善するだけでは到達できません。

必要な実装:

```text
editor/extensions/
├── activeBlock.ts
├── syntaxVisibility.ts
├── headingDecoration.ts
├── emphasisDecoration.ts
├── blockquoteDecoration.ts
├── listDecoration.ts
├── linkDecoration.ts
└── codeBlockDecoration.ts
```

---

## 理由B: タスクチェックボックスなどを「表示から直接操作」できない

現在のPreviewではチェックボックスが表示されますが、プレビューは編集面ではありません。

Typora型では、

```md
- [ ] 未完了
- [x] 完了
```

をチェックボックスとして表示し、クリックするとMarkdown原文の空白または`x`だけが更新される必要があります。

未実装:

- CodeMirror Decoration Widgetによるチェックボックス表示
- クリック時の原文更新
- Widget操作のUndo / Redo
- キーボード操作とアクセシビリティ
- IME変換中のWidget再生成抑制

---

## 理由C: Markdown構造解析が二重化され、片方は限定的である

現在は役割の異なる2つの解析経路があります。

```text
プレビュー:
  react-markdown + remark-gfm
  → 比較的完全なCommonMark / GFM解析

既存機能への投影:
  src/markdown.ts の独自パーサー
  → 見出し、段落、画像、Fence、Mermaidを中心とした限定解析
```

このため、プレビューでは正しく見えても、AI・スライド・段落エディタ側では同じ構造として理解されないMarkdownがあります。

例:

- ネストしたリスト
- 複数段落を含むリスト項目
- Setext見出し
- 参照リンク
- 脚注
- 複雑なFence
- HTMLブロック
- Markdown表
- 引用内の複合ブロック

必要なのは、`remark / unified`のASTを構造解析の共通基盤にすることです。

```text
Markdown source
      ↓
remark AST（唯一の構造解析結果）
      ├─ Preview
      ├─ Outline
      ├─ Chunk projection
      ├─ Slide projection
      └─ AI context map
```

原文は引き続き唯一の正本とし、ASTとチャンクは派生物にします。

---

## 理由D: 外部変更検知と保存競合の解決がない

Rust側のアトミック保存は実装済みですが、別アプリやGit操作で同じMarkdownファイルが変更された場合の検知がありません。

危険なケース:

```text
1. NurumayuEditorでnote.mdを開く
2. 別のエディタやgit pullでnote.mdが変更される
3. NurumayuEditorで保存する
4. 外部変更を知らずに上書きする
```

Typoraの代替として常用するには、このデータ損失リスクを先に解消する必要があります。

未実装:

- ファイルの更新時刻・サイズ・内容ハッシュによるRevision管理
- Rust `notify`による外部変更監視
- 自分自身の保存イベントとの区別
- 外部変更時の自動上書き停止
- 「再読み込み」「現在の内容を維持」「差分を比較」の選択UI
- 保存時のexpected revisionチェック

---

## 理由E: セッション復旧はあるが、Markdownファイルの自動保存ではない

現在の自動保存は、クラッシュ復旧用のセッション保存です。

これは重要ですが、編集中のMarkdownファイル自体を自動保存する機能とは異なります。

未実装:

- Markdownファイルへのデバウンス付き自動保存
- 自動保存中・保存済み・競合中の状態表示
- 外部変更がある場合の自動保存停止
- 自動保存失敗の永続表示
- 設定でAuto / Offを選択する仕組み

自動保存を追加する場合は、外部変更検知より先に実装してはいけません。競合検知なしの自動保存は、上書き事故を自動化するためです。

---

## 理由F: 見出しアウトラインがない

長いMarkdown文書を常用する場合、見出し間の移動が必要です。

未実装:

- ASTからの見出し一覧生成
- H1〜H6の階層表示
- クリックによる編集位置への移動
- 現在位置に応じたアクティブ見出し表示
- 編集中のリアルタイム更新
- 折りたたみ

現在AI用の文書マップはありますが、ユーザーが操作するアウトラインUIとは別物です。

---

## 理由G: 検索・置換とMarkdown編集コマンドが不足している

CodeMirror自体には拡張がありますが、現在のNurumayuEditorには常用エディタとして必要な編集機能が十分に接続されていません。

不足項目:

- 文書内検索
- 置換、すべて置換
- 大文字小文字・正規表現オプション
- 選択範囲を太字・斜体・リンク・コードにする操作
- 見出しレベル変更
- リスト化、引用化
- リストのインデント・アウトデント
- リンク挿入
- コードFence挿入
- Markdown用コマンドパレット項目

Typora型の操作感には、記号を手入力しなくても主要な構造を作れることも含まれます。

---

## 理由H: 相対パス画像を安全に解決できない

Markdownでは次のような相対パス画像が一般的です。

```md
![結果](./images/result.png)
```

現在のWebViewプレビューでは、Markdownファイルの保存場所を基準にしてローカル画像を安全に解決する仕組みがありません。

必要な実装:

- Markdownファイルの親ディレクトリを基準にしたパス解決
- Rust側の許可済みパス読み込みCommand
- data URLまたは安全なasset protocolへの変換
- `..`を含むパストラバーサル対策
- ファイル移動時の再解決
- 見つからない画像のエラー表示
- Preview / PDF / PPTXで同じ画像解決規則を使う契約テスト

---

## 理由I: Previewと各種出力が同じレンダリング契約ではない

Markdown Previewは`react-markdown`で描画します。

一方、PDFやPPTXなどはチャンクモデルを元に別経路で生成します。

そのため、次の差が起きる可能性があります。

- ネストしたリストの構造が出力で変わる
- GFMテーブルがPDF / PPTXに反映されない
- タスクリストの見た目が違う
- コードブロックの言語情報や装飾が違う
- 画像解決が違う
- Markdown Previewでは見えるが出力では欠落する

Typoraに近い完成度を名乗るには、「プレビューで見たもの」と「保存・印刷・書き出し」の契約を明確にする必要があります。

すべてを完全一致させる必要はありませんが、未対応要素は警告レポートに残し、黙って落としてはいけません。

---

## 理由J: テーマ、表示設定、アクセシビリティが未完成

未実装または不足:

- ダークテーマ
- OSテーマ追従のAuto
- MarkdownソースとPreviewのフォント設定統一
- Preview文字サイズ設定
- コントラスト検証
- キーボードだけでの全操作
- スクリーンリーダー向けの編集・プレビュー状態通知
- 分割幅の調整
- 狭いウィンドウでのレスポンシブ切り替え

Typoraは長時間使う執筆アプリなので、単に表示できるだけでなく、疲れずに使えることが完成度に含まれます。

---

## 理由K: 大規模文書と日本語IMEの耐久検証が不足している

現在のMarkdown編集では、入力のたびにMarkdownからチャンクへの投影を更新します。

短い文書では問題ありませんが、数万〜数十万文字の文書では次がリスクになります。

- キー入力ごとの全文解析
- React Previewの全文再描画
- Mermaidブロックの再描画
- チャンクIDやメタデータの安定性
- Undo履歴のメモリ使用量
- 日本語IME変換中の再解析

必要な検証:

- 1万、10万、50万文字の入力遅延
- 1000見出しのアウトライン更新時間
- 100個のコードブロックを含む文書
- IME composition中の変換確定・取り消し
- 長文でのUndo / Redo
- タブ切り替え後のカーソル復元

---

## 理由L: 対応するMarkdown方言の境界が未定義

現在はCommonMark + GFMを中心にしていますが、次の扱いが未決定です。

- 脚注
- 数式（インライン / ブロック）
- YAML Front Matter
- 目次記法
- Wiki Link
- 生HTML
- PlantUMLなどMermaid以外の図
- GitHub Alerts / Callouts

全部を実装する必要はありません。

必要なのは、

```text
対応
表示のみ
ソース保持のみ
非対応
```

の境界を明文化し、プレビューと保存で予測可能にすることです。

## 4. 実装優先順位

## Phase B0: データ安全性

最優先。ここが終わるまでファイル自動保存は追加しません。

実装:

1. `DocumentState`へ次を追加

```ts
interface MarkdownFileState {
  path: string | null;
  source: string;
  savedSource: string;
  revision: string | null;
  lineEnding: "\n" | "\r\n";
  encoding: "utf-8";
  externallyModified: boolean;
}
```

2. Rust側へファイルRevision取得を追加
3. `notify`によるWatcherを追加
4. 保存Commandへ`expectedRevision`を渡す
5. Revision不一致時は保存を拒否
6. 外部変更の選択UIを追加
7. 差分表示へ接続

完了条件:

- 外部変更されたファイルを黙って上書きしない
- 自分自身の保存を外部変更として誤検知しない
- 再読み込み、維持、比較の3つを選べる
- 競合と失敗がHealth Barに残る
- RustとFrontendのRevision型に契約テストがある

---

## Phase B1: Markdown構造の一本化

実装:

1. `unified + remark-parse + remark-gfm`を構造解析の正本にする
2. 独自パーサーをASTベースのprojectionへ置換する
3. ASTからOutlineを生成する
4. ASTからAI用document mapを生成する
5. ASTからスライド用projectionを生成する
6. Markdown原文は変換せず保持する

完了条件:

- PreviewとChunk projectionが同じMarkdown構造を参照する
- ネストしたリスト、引用、表、Fenceを誤って別チャンクへ分解しない
- 日本語・参照リンク・末尾空白を含むfixtureがラウンドトリップする
- export→import→exportの2周目でも原文が増殖・変形しない

実装:

- カーソル位置とスクロール位置のタブ別保存
- 分割ペインの幅調整
- Preview側見出しクリックからソース位置への移動

完了条件:

- 1万行の文書で見出しを即座に移動できる

- 検索・置換が日本語と正規表現で動く

## Phase B3: Typora型WYSIWYM

実装順:

1. `activeBlock.ts`

3. 太字・斜体・打ち消し線

## 5. Typora相当を名乗るためのDefinition of Done

次をすべて満たした時点で「Typoraに近い」と表現できます。

### 編集体験

- 1つの編集面でMarkdown記号を必要時だけ表示できる
- 見出し、強調、引用、リスト、リンク、コードがWYSIWYM表示になる
- タスクチェックボックスを直接操作できる
- 日本語IMEで不具合がない

### ファイル安全性

- Markdown原文が正本である
- 外部変更を検知する
- 競合時に黙って上書きしない
- UTF-8、LF / CRLF、末尾空白を保持する
- 保存はアトミックである

### 文書操作

- Outlineがある
- 検索・置換がある
- Markdown編集Commandがある
- 相対画像を表示できる
- 複数タブで状態が混ざらない

### Preview / Export

- Previewと構造解析が同じASTを使う
- Previewと出力の対応範囲が明文化されている
- 欠落する要素は永続的な警告として報告される

### 品質

- 10万文字級の文書で性能検証済み
- CJKと混在文でテスト済み
- WYSIWYM Decorationのカーソル・Undo・IMEテストがある
- 外部変更、保存失敗、画像欠落の失敗系テストがある

## 7. 推奨する次の着手順

最も安全で効果の高い順番は次です。

```text
1. 外部変更検知とRevision保存
2. remark ASTへの構造解析一本化
3. Outline
4. Search / Replace
5. 相対画像
6. Markdown編集Command
7. 見出しからWYSIWYMを段階導入
8. 強調・リンク・リスト・チェックボックス
9. 自動保存
10. Dark / Autoテーマと長文最適化
```

WYSIWYMを最初に実装すると見た目はTyporaに近づきますが、外部変更による上書きや解析経路の不一致が残ります。

そのためPlan Bでは、

```text
データを失わない
→ 構造を一本化する
→ 日常操作を完成させる
→ Typora型表示を載せる
```

という順序を採用します。

この順序なら、各Phaseの終了時点で常に実用価値が上がり、途中の状態でも安全にリリースできます。
